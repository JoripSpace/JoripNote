# JoripNote Notion 가져오기 정합성 개선 설계 및 구현 프롬프트

## 1. 실제 화면·데이터 감사 결과

2026-09-10에 원본 Notion의 `팀 작업` 페이지와 JoripNote의 가져온 결과를 비교했다.

- 원본 `팀 작업`은 페이지 설명, 아이콘, 여러 데이터베이스 뷰(담당자별·상태별 보드, 전체/개인 작업, 테이블, 피드), 필터·정렬, 타입이 있는 속성을 포함한다.
- JoripNote에서는 `팀 작업` Markdown 문서와 `팀 작업 fb48800b383540ceb55e185131f95f7b_all` CSV 문서가 분리되어 생성된다.
- 가져온 데이터베이스는 대부분의 속성이 텍스트가 되고, 기본 테이블 뷰 하나만 생성된다.
- 현재 운영 데이터에 `_all` CSV 동반 문서가 45개, `제목 없음`·`홈`·`내 작업` 같은 모호한 제목이 43개, 데이터베이스 블록이 62개 있다.
- 변환되지 않고 본문에 그대로 노출된 URL 인코딩 상대 링크 패턴이 1,457개 있다.
- `팀 작업` 부모 문서에 실제로는 자식 문서 소유인 이미지 3개가 붙었다. 원인은 자식 디렉터리 이름 끝의 공백과 문서 파일명 정규화 차이로 정확한 소유 문서를 찾지 못한 뒤 상위 문서로 조용히 폴백한 것이다.
- Markdown/CSV 내보내기 파일에는 Notion의 모든 메타데이터가 들어 있지 않다. 페이지 설명, 정확한 데이터베이스 뷰 구성, 일부 아이콘·커버, 관계형 속성 스키마는 ZIP만으로 완전 복원이 불가능할 수 있다.

## 2. 목표와 원칙

목표는 픽셀 단위 복제가 아니라 다음 우선순위의 의미적 정합성이다.

1. 문서·데이터베이스·첨부파일이 올바른 부모와 소유자에 연결된다.
2. 사용자에게 깨진 상대 링크, `_all` 보조 문서, 엉뚱한 이미지가 보이지 않는다.
3. ZIP에 있는 블록 구조와 인라인 서식을 최대한 보존한다.
4. 데이터베이스 행·속성·대표 뷰가 실제 업무에 사용할 수 있는 형태로 복원된다.
5. ZIP에 없는 정보는 임의로 사실처럼 만들지 않는다. 추정값은 표시하고, 완전 복원이 필요하면 선택적 Notion API 연결을 사용한다.
6. 기존 가져오기 결과와 사용자가 이후 수정한 내용을 삭제하거나 덮어쓰지 않는다.

## 3. 제안 아키텍처

### A. 가져오기 전용 정규화·매니페스트 단계

ZIP 중앙 디렉터리를 읽은 뒤 업로드 전에 모든 항목을 정규화한 canonical manifest를 만든다.

- 각 경로 세그먼트에 URL decode, Unicode NFKC, CR/LF 제거, 끝 공백·점 제거를 일관되게 적용한다.
- 문서 파일명의 끝 32자리 Notion page ID를 추출해 `source_page_id`로 저장한다.
- `<page-id>_all.csv`는 독립 문서가 아니라 해당 데이터베이스 페이지의 동반 데이터 파일로 인식한다.
- 파일명/폴더명이 달라도 page ID를 최우선 키로 사용한다. ID가 없을 때만 정규화한 전체 경로를 사용한다.
- 첨부파일은 가장 가까운 문자열 경로가 아니라 명시적으로 결정된 page ID에 연결한다.
- 소유자를 유일하게 결정할 수 없는 첨부파일은 상위 문서로 조용히 폴백하지 말고 `unresolved`로 격리해 가져오기 보고서에 표시한다.
- 동일 source identity에 대한 재실행은 새 문서를 만들지 않는 upsert여야 한다.

### B. CSV 동반 파일 병합

- Markdown에서 같은 페이지 ID의 `_all.csv` 링크를 발견하면 링크 블록 대신 데이터베이스 블록을 부모 문서에 삽입한다.
- `_all.csv`는 사이드바 문서로 만들지 않고 `consumed_artifact` 상태로 기록한다.
- 기존에 생성된 45개 `_all` 문서는 안전한 복구 작업에서 부모 문서로 병합한다.
- CSV의 Name/제목 셀과 하위 Markdown 페이지의 source page ID를 연결해 데이터베이스 행에서 실제 JoripNote 문서를 열 수 있게 한다.
- 헤더와 값으로 `date`, `number`, `checkbox`, `url`, `select/status`, `person`, `attachment` 타입을 보수적으로 추론한다. 확신이 낮으면 텍스트로 두되 가져오기 보고서에 표시한다.
- `상태`처럼 명확한 열은 값 전체를 스캔해 선택 옵션을 생성하고 기본 보드 뷰를 제공한다.

### C. 데이터베이스 모델 확장

현재 단일 `view`와 제한적인 셀 모델을 다음처럼 확장한다.

- `views[]`: table/board, 이름, groupBy, filter, sort, visibleColumns, order를 저장한다.
- 기존 단일 view 문서는 자동 마이그레이션한다.
- `relation/page`, `attachment`, `multi_select`, `created_time`, `last_edited_time`을 지원한다.
- ZIP만 사용한 경우 원본 뷰 구성을 알 수 없으므로 `전체 보기` 테이블과, status/select가 있으면 `상태별` 보드를 생성하고 UI에 `가져오기에서 생성된 보기`라고 표시한다.
- 정확한 원본 뷰·속성 스키마는 선택적 Notion API 동기화가 연결된 경우에만 복원한다.

### D. Markdown 변환기를 줄 단위 파서에서 AST 기반 파서로 교체

다음을 보존하는 테스트 가능한 parser/transformer 계층을 만든다.

- 여러 줄 문단과 강제 줄바꿈
- 중첩 bullet/numbered/todo와 indent level
- fenced code language
- 표, 인용, 구분선, callout, toggle/details, 수식
- 인라인 bold/italic/strike/code/link
- 이미지 alt/caption, 파일·오디오·동영상·bookmark
- 내부 문서 링크와 앵커

DB에 저장할 때 500블록으로 조용히 자르지 않는다. 문서 한도를 초과하면 연속된 섹션 문서로 분할하거나 명시적인 실패/경고를 제공한다.

### E. 링크와 첨부파일 정합성

- 상대 링크 해석은 URL 인코딩/이중 인코딩, `#anchor`, 공백·괄호, 대소문자 차이를 처리한다.
- 변환 후 저장 직전에 모든 내부 상대 링크를 검증한다. 해결되지 않은 링크는 원문과 이유를 import issue로 기록한다.
- Markdown에 명시적으로 등장한 첨부파일만 해당 위치에 블록으로 만든다.
- 연결은 됐지만 본문에서 참조되지 않은 파일은 문서 상단에 이미지를 임의로 추가하지 말고 `가져온 파일` 패널에 둔다.
- HTML, SVG, JS처럼 렌더링이 차단된 파일도 삭제하지 말고 이름·크기·차단 이유를 보고서에 남긴다.

### F. ZIP 한계를 보완하는 선택적 Notion API 모드

ZIP 가져오기는 기본이자 오프라인 경로로 유지한다. 사용자가 원본과 더 높은 정합성을 원할 때만 공식 Notion integration을 연결한다.

- 토큰은 JoripSpace Secret binding에만 저장하고 소스·로그·DB 평문에 두지 않는다.
- page/database ID를 기준으로 아이콘, 커버, description, property schema, relation, view metadata 중 공식 API가 제공하는 항목만 보강한다.
- API가 제공하지 않는 view 정보는 복원했다고 표시하지 않는다.
- 연결 전후 예상 복원 범위를 UI에서 설명한다.

## 4. 기존 운영 데이터 안전 복구

새 변환기 배포만으로 기존 3,056개 문서는 바뀌지 않으므로 `재검사 및 복구` 작업이 필요하다.

- `source_page_id`, `source_path`, `import_id`, `import_baseline_snapshot_id`, `transform_version`을 영속화한다.
- 가져오기 후 사용자가 수정하지 않은 문서는 제자리에서 새 snapshot/version으로 교정한다.
- 현재 snapshot이 import baseline과 다르면 자동 덮어쓰지 않고 충돌 목록에 넣어 `기존 유지`, `가져오기 결과로 교체`, `복제 후 비교`를 선택하게 한다.
- 잘못 연결된 첨부파일은 올바른 소유 문서로 재연결하되 R2 객체를 중복 업로드하지 않는다.
- `_all` 문서는 부모 데이터베이스에 병합된 뒤 바로 삭제하지 말고 7일간 숨김 복구 상태로 유지한다.
- 복구 전후 문서 수, 데이터베이스 수, 첨부파일 수, 해결/미해결 링크 수를 기록한다.

## 5. 가져오기 결과 UI

완료 토스트 한 줄 대신 영구적인 결과 화면을 제공한다.

- 요약: 문서, 데이터베이스, 행, 첨부파일, 내부 링크, 경고, 실패
- 경고 필터: 소유자 미확정 파일, 깨진 링크, 타입 추론, ZIP에 없는 Notion 메타데이터
- 각 경고에서 원본 경로와 대상 JoripNote 문서로 이동
- 같은 ZIP 재실행 시 `새로 만들기`가 아니라 `검사 및 복구`로 표시
- 화면 상단에 `ZIP 복원`과 `Notion 연결로 보강`의 차이를 설명

## 6. 수용 기준

- 실제 운영 ZIP을 재검사했을 때 `_all` 사이드바 문서가 0개다.
- `%ED...csv` 같은 raw 상대 링크가 본문에 0개다.
- 자식 디렉터리의 파일이 부모 문서에 잘못 연결된 사례가 0개다.
- `팀 작업` 문서 안에서 데이터베이스가 보이고, status 값으로 보드 보기가 동작한다.
- 데이터베이스 행 제목에서 해당 하위 문서를 열 수 있다.
- 날짜·숫자·체크박스·URL·상태가 올바른 셀 타입으로 저장된다.
- 중첩 목록, 코드 언어, 표, callout, 내부 링크, 이미지 위치를 fixture 테스트로 검증한다.
- 재실행해도 문서·파일·행이 중복되지 않는다.
- 사용자가 가져오기 후 수정한 문서는 자동 복구가 덮어쓰지 않는다.
- 실패/경고가 UI와 로그에 source path 및 안전한 오류 코드로 남는다.
- 기존 인증, 권한, 공개 문서, 버전 복원 테스트와 신규 회귀 테스트가 모두 통과한다.

## 7. 구현용 프롬프트

아래 프롬프트를 구현 에이전트에게 그대로 전달한다.

```text
JoripSpace 프로젝트 `cf-notion-st`의 JoripNote Notion 가져오기 정합성을 개선하고 기존 운영 데이터를 안전하게 복구해 배포해줘.

먼저 현재 세션에서 `joripspace start cf-notion-st --cwd <현재 Git 루트> --json`을 실행하고 반환된 onboarding 문서와 AGENTS.md를 모두 읽어라. 기존 사용자 변경을 보존하고, JoripSpace 인프라·DB 마이그레이션·배포에는 공식 CLI만 사용하라. 인증 토큰이나 외부 서비스 secret을 소스, 로그, 문서에 남기지 마라.

작업 전 `docs/notion-import-parity-plan.md` 전체를 읽고 이를 요구사항과 수용 기준으로 사용하라. 실제 운영 감사에서 확인된 핵심 결함은 다음과 같다.

1. Notion 데이터베이스 Markdown과 `<page-id>_all.csv`가 별도 문서로 생성된다. 운영 DB에 `_all` 문서가 45개 있다.
2. URL 인코딩된 상대 링크가 본문에 그대로 남은 패턴이 1,457개 있다.
3. 경로 세그먼트의 끝 공백 차이 때문에 자식 문서 이미지가 부모 문서에 연결된다. 소유자 탐색 실패 시 조용히 상위 문서로 폴백하면 안 된다.
4. CSV 속성이 대부분 text로 평탄화되고 원본의 보드/테이블 의미가 사라진다.
5. 현재 Markdown 파서는 줄 단위라 중첩 목록, 여러 줄 문단, 코드 언어, 표, callout, toggle, 수식, 인라인 서식을 충분히 보존하지 못한다.
6. ZIP에 없는 Notion 전용 메타데이터는 완전 복원할 수 없으므로 ZIP 복원과 선택적 공식 Notion API 보강을 명확히 분리해야 한다.

다음 순서로 구현하라.

A. 테스트 fixture부터 만든다. page ID가 포함된 Markdown+`_all.csv`, 끝 공백이 있는 폴더, 중첩 블록, 내부 링크, 이미지, 타입 추론용 CSV를 최소 fixture로 추가한다.
B. canonical manifest와 source identity를 구현한다. 모든 경로 세그먼트에 URL decode/NFKC/끝 공백 정규화를 적용하고, 파일명의 32자리 page ID를 최우선 연결 키로 사용한다.
C. `_all.csv`를 독립 문서로 만들지 말고 부모 페이지 안의 데이터베이스로 병합한다. 데이터베이스 행 제목은 같은 page ID/정규화 경로의 하위 문서에 연결한다.
D. 첨부파일 소유자를 명시적으로 결정한다. 유일하게 결정되지 않으면 unresolved issue로 남기며 부모에 임의 부착하지 않는다. 본문에 없는 파일은 문서 블록 끝에 임의 추가하지 말고 별도 가져온 파일 패널에서 보여준다.
E. CSV 타입 추론과 database model의 views 배열을 구현한다. ZIP 모드에서는 전체 테이블 및 명확한 status/select 열이 있을 때 상태별 보드를 생성하고 추정 보기임을 표시한다. 정확한 원본 view라고 주장하지 않는다.
F. Markdown을 AST 기반 변환기로 바꾸고 여러 줄 문단, 중첩 목록/todo, fenced code language, 표, 인용, divider, callout, toggle, 수식, inline marks/link, media caption을 보존한다. 500블록 silent truncation을 제거한다.
G. 모든 내부 링크를 최종 검증하고 해결되지 않은 링크와 이유를 import issue에 기록한다.
H. import provenance와 baseline snapshot을 저장하는 마이그레이션을 추가하고, 운영 세션의 기존 3,056개 문서를 위한 재검사/복구 흐름을 구현한다. 사용자가 import 이후 수정한 문서는 절대 자동 덮어쓰지 말고 충돌로 분리한다. 파일은 R2에서 재업로드하지 않고 재연결한다. `_all` 문서는 병합 후 7일간 복구 가능한 숨김 상태로 유지한다.
I. 가져오기 보고서 화면을 추가해 문서/DB/행/파일/링크/경고/실패 수와 개별 source path를 보여준다.
J. 선택적 Notion API 보강은 공식 API가 실제 제공하는 메타데이터만 대상으로 설계·구현하고 토큰은 JoripSpace Secret binding에만 저장한다. API 문서를 확인해 지원되지 않는 view 정보를 추측하지 않는다. 이 연결이 이번 범위를 과도하게 키우면 별도 feature flag 뒤에 인터페이스와 보안 저장 경로까지만 만들고 ZIP 정합성 개선을 먼저 완성한다.

구현 시 단일 `worker.js`에 기능을 더 밀어 넣지 말고 importer/parser/database-view/report 모듈로 분리하되 기존 esbuild 배포 구조는 유지하라. 마이그레이션은 추가 방식으로 작성하고 파괴적 변경을 피하라. 실제 운영 데이터 복구 전에 dry-run 보고서를 생성해 건수를 검증하라.

검증은 `npm run lint`, `npm test`, `npm run build`와 신규 fixture 테스트를 수행한다. dry-run에서 `_all` 문서, raw 상대 링크, 잘못된 첨부파일 소유자, 충돌 문서 수를 보고한다. 복구는 dry-run 결과가 수용 기준과 일치할 때만 실행하고, 배포 후 `https://cf-notion-st.joripspace.run/`에서 `팀 작업` 문서를 원본 Notion 화면과 비교 검증한다. 최종 보고에는 마이그레이션, 자동 교정/충돌/미해결 건수, 테스트 결과, 배포 ID, 운영 URL, ZIP 자체 한계로 남은 차이를 포함하라.
```

## 8. 권장 실행 순서

한 번에 모두 고치기보다 다음 세 배포로 나누는 편이 안전하다.

1. P0 정합성: page ID 기반 매핑, 경로 정규화, `_all.csv` 병합, raw 링크 해결, 첨부파일 오연결 차단, dry-run/보고서.
2. P1 표현력: AST Markdown 변환, typed database, table/board views, 행→문서 연결.
3. P2 고급 보강: 기존 데이터 충돌 UI, 선택적 Notion API 연결, 아이콘·커버·제공 가능한 메타데이터 동기화.
